Concept

Two separate jobs: what to compare, and how to compare fast

Think of a librarian who has skimmed every chunk in the document and roughly remembers what each one is about. Ask a question, and instead of you reading every chunk yourself, the librarian instantly points you to the ones that are actually relevant — even if your question doesn't use the same words as the text. That's what this stop builds, in two steps.

1

Turn text into numbers

An embedding model reads a chunk and turns it into 384 numbers describing what it means. Two chunks about the same idea end up with similar numbers, even with zero words in common — that's what lets "forecast error was 3.2%" match a question about "accuracy" with no keyword overlap at all.

↓
2

Find the closest numbers, fast

A question gets turned into 384 numbers the same way. FAISS's job is to instantly find which chunks' numbers sit closest to the question's. Checking a handful of chunks by hand would be fine — checking thousands one by one isn't — so FAISS builds a structure that skips straight to the nearest matches.

This project makes two specific, deliberate choices here: embeddings run locally with sentence-transformers/all-MiniLM-L6-v2 (free, no API key, nothing leaves your machine), and FAISS runs as an in-process library rather than a hosted database. Both trade a little quality and scale for zero-cost, zero-setup — the right call for a project anyone should be able to clone and run for free. The index is cached to disk with save_local(), so it's only built once: every app launch after the first loads the cache instead of re-embedding the whole PDF.

def get_embeddings() -> HuggingFaceEmbeddings:
    """Load the local sentence-transformers embedding model."""
    return HuggingFaceEmbeddings(model_name=config.EMBEDDING_MODEL_NAME)


def build_vectorstore(pdf_path: Path = config.DEFAULT_PDF_PATH) -> FAISS:
    """Build a fresh FAISS index in memory from the source PDF."""
    chunks = load_and_split(pdf_path)
    embeddings = get_embeddings()
    return FAISS.from_documents(chunks, embeddings)


def save_vectorstore(vectorstore: FAISS, path: Path = config.VECTORSTORE_DIR) -> None:
    """Persist a FAISS index to disk so it doesn't need to be rebuilt."""
    path.mkdir(parents=True, exist_ok=True)
    vectorstore.save_local(str(path))


def load_vectorstore(path: Path = config.VECTORSTORE_DIR) -> FAISS:
    """Load a previously saved FAISS index from disk."""
    embeddings = get_embeddings()
    return FAISS.load_local(
        str(path), embeddings, allow_dangerous_deserialization=True
    )


def get_or_build_vectorstore(
    pdf_path: Path = config.DEFAULT_PDF_PATH,
    vectorstore_path: Path = config.VECTORSTORE_DIR,
) -> FAISS:
    """Load a cached index if one exists; otherwise build and cache one."""
    index_file = vectorstore_path / "index.faiss"
    if index_file.exists():
        return load_vectorstore(vectorstore_path)
    vectorstore = build_vectorstore(pdf_path)
    save_vectorstore(vectorstore, vectorstore_path)
    return vectorstore

allow_dangerous_deserialization=True is required because a FAISS index loads via pickle. It's safe here because the only index ever loaded is one this project itself created — never load a FAISS index you didn't build or don't trust.

get_or_build_vectorstore() is the function everything else actually calls. Embedding a PDF is the slowest step in the whole pipeline; checking for index.faiss first is what makes every app launch after the first one instant.

For beginners

Why this vector store, and what else fits?

FAISS is a library, not a server — it runs inside your Python process and saves to a folder on disk. That's perfect for one person, one document, running locally: no server to host, no account to create. It starts to fall short once you need things a database gives you for free — multiple people writing at once, deleting/updating individual chunks without rebuilding the whole index, or running across many machines.

OptionUse it when
FAISS — used in this projectOne person, one document, running locally — no server to host, no account to create.
ChromaYou want something almost as simple as FAISS but with easier add/update/delete of individual chunks.
Pinecone / Weaviate / QdrantYou need a hosted, managed vector store — multiple users, production scale, no server ops.
pgvectorYou already run Postgres and want vectors alongside your normal relational data.

Why this embedding model, and what else fits?

Every embedding model makes the same underlying trade: where it runs, versus what it costs and how good the vectors are. A model that runs on your own machine is free and keeps every chunk of your document private — nothing is ever sent anywhere. A hosted embedding API usually produces higher-quality vectors and handles more languages, at the cost of a per-call fee, an API key, and a network round-trip for every chunk you embed. Neither is universally "better" — it depends on whether you're optimizing for zero-cost/zero-setup or for maximum retrieval quality at scale.

Quiz

Check yourself

1. Why use a local embedding model instead of a hosted embeddings API?

The trade-off is explicit: slightly lower quality and slower than a hosted API, in exchange for zero-cost, zero-key setup.

2. What happens if you query a FAISS index with a different embedding model than the one that built it?

FAISS just stores numbers — it has no idea which model produced them, so a mismatch fails silently.

3. Why cache a vector index to disk instead of rebuilding it from scratch every time the app starts?

Rebuilding the index means re-embedding every chunk from scratch. Checking for a saved index first is what makes every launch after the first one instant.
