Concept

The UI is a thin shell, not the pipeline

app.py is the only file that imports Streamlit. It never builds a prompt, calls FAISS, or talks to the LLM directly — it imports the already-finished pipeline from rag.py and config.py and renders it. That separation means the UI layer could be swapped for a CLI, a FastAPI endpoint, or a different frontend without touching a single line of RAG logic.

Two Streamlit-specific concerns show up here that don't exist anywhere else in the project: caching (Streamlit reruns the entire script on every interaction, so the expensive chain-building step has to be explicitly protected from re-running on every keystroke) and graceful failure (a model that isn't running yet should produce a clear in-app message, not a raw Python stack trace).

st.set_page_config(page_title="PDF Q&A", page_icon="📄")
st.title("📄 PDF Q&A")

@st.cache_resource(show_spinner="Building the index...")
def load_chain():
    vectorstore = get_or_build_vectorstore()
    return build_rag_chain(vectorstore)

ollama_ready, ollama_message = check_ollama_ready()
if not ollama_ready:
    st.error(ollama_message)
    st.stop()

chain = load_chain()
question = st.text_input("Ask a question about the document:")

if question:
    with st.spinner("Thinking..."):
        answer, sources = answer_question(chain, question)

    st.subheader("Answer")
    st.write(answer)

    st.subheader("Source chunks")
    for i, doc in enumerate(sources, start=1):
        page = doc.metadata.get("page", "unknown")
        with st.expander(f"Chunk {i} — page {page}"):
            st.write(doc.page_content)

@st.cache_resource is doing real work here: Streamlit reruns the whole script top to bottom on every interaction. Without this decorator, load_chain() — and the potentially slow get_or_build_vectorstore() inside it — would re-run on every single keystroke in the text box.

The readiness guard runs before load_chain() is called, not after. check_ollama_ready() (introduced in Stop 4) makes one lightweight local call to confirm the model server is up and the model is actually pulled, so a not-yet-running local model produces one clear sentence instead of a connection-error stack trace from deep inside the LLM client.

Each source chunk renders inside its own st.expander, labeled with its page number — this is what lets a reader verify the answer against the original document instead of just trusting it.

For beginners

Why this UI framework, and what else fits?

Streamlit turns a plain Python script into a web app with no HTML, CSS, or JavaScript — st.text_input(...) and st.write(...) above are the entire frontend. That makes it the fastest way to get a usable interface on top of a finished Python pipeline, at the cost of limited control over layout and styling compared to a real frontend framework.

OptionUse it when
Streamlit — used in this projectYou want a usable interface on a finished Python pipeline fast, with no HTML/CSS/JS.
GradioVery similar trade-off to Streamlit; common for ML/AI demos specifically.
Flask / FastAPI + a frontendYou need a real API, custom design, or a mobile app to talk to the backend — much more setup, full control.
Just a CLI (input() loop)You're the only user and a browser adds nothing — good enough while still developing the pipeline itself.

Quiz

Check yourself

1. Why check that a required dependency (like a local model server) is ready early and fail with a clear message, instead of letting the app crash deeper in the code?

Checking early turns an opaque connection error buried deep in a library call into one readable sentence for the user.

2. Why does an app that rebuilds its entire UI on every interaction need to cache expensive setup steps?

Frameworks like this rerun the whole script on every interaction — without caching, that means rebuilding the whole pipeline every time the user types a single character.

3. Why is it good practice to keep the UI layer separate from the retrieval and generation logic?

A thin UI shell over a finished pipeline means the frontend is swappable — a CLI or API frontend could replace it without touching the RAG logic at all.
