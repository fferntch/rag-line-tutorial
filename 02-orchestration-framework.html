Concept

From raw PDF to chunks, in three steps

A whole PDF page is usually too big and too topically mixed to be a good unit of retrieval — if a page covers three different subtopics, a question about one of them still pulls in the other two as noise. Getting from a raw PDF to something retrieval can actually use covers three concepts:

  1. Document loading — PyPDFLoader opens the PDF and reads it page by page.
  2. Preprocessing — each page's raw content gets extracted into plain text, with page number and source path attached as metadata. This happens automatically inside PyPDFLoader.load() — there's no separate preprocessing function in this project, but it's worth naming as its own concept, since not every loader does it cleanly (some leave you with garbled text from scanned PDFs or complex layouts — see the loader comparison below). The result is one Document per page: a simple LangChain object with just two parts, page_content (the page's text) and metadata (the dict holding source path and page number) — that's the entire shape of the object passing through this stop.
  3. Text chunking — RecursiveCharacterTextSplitter breaks each page's Document into several smaller ones: ~1000-character chunks with 200 characters of overlap, preferring to cut on paragraph or sentence boundaries rather than mid-word.

The overlap matters: without it, a sentence that happens to fall right on a chunk boundary gets split in half, and half a sentence embeds and retrieves worse than a whole one. Repeating the last 200 characters of one chunk at the start of the next means that boundary sentence almost always survives intact in at least one of the two chunks.

loader.pyPython
from pathlib import Path
from typing import List

from langchain_community.document_loaders import PyPDFLoader
from langchain_core.documents import Document
from langchain_text_splitters import RecursiveCharacterTextSplitter

from config import CHUNK_OVERLAP, CHUNK_SIZE


def load_pdf(pdf_path: Path) -> List[Document]:
    loader = PyPDFLoader(str(pdf_path))
    return loader.load()


def split_documents(documents: List[Document]) -> List[Document]:
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=CHUNK_SIZE,
        chunk_overlap=CHUNK_OVERLAP,
        separators=["\n\n", "\n", ". ", " ", ""],
    )
    return splitter.split_documents(documents)

separators=["\n\n", "\n", ". ", " ", ""] is tried in order — the splitter first tries to cut on paragraph breaks, then line breaks, then sentence ends, then spaces, and only falls back to a hard character cut ("") if nothing else fits within chunk_size. That's why the example above breaks cleanly at a sentence, not mid-word.

Each returned chunk keeps the metadata from its parent page Document (source path, page number) — this is exactly what lets the UI later show "page 12" next to a retrieved chunk.

This module never touches embeddings or an LLM. Loading and splitting is pure data preparation, which is what makes it independently testable.

For beginners

Why this orchestration framework, and what else fits?

You could call a model's API directly, load a PDF yourself, and write your own loop to search for relevant text. A framework doesn't do anything you couldn't write by hand — it just gives standard, pre-built pieces (loaders, splitters, vector store wrappers, chains) for steps that almost every RAG project needs, so you're not reinventing PDF parsing or prompt assembly from scratch. The trade-off is an extra dependency to learn and occasional "magic" behind an abstraction — worth it for a first project; some teams later strip it out once they know exactly what they need.

OptionTrade-off
LangChain — used in this projectBroadest ecosystem of pre-built loaders, splitters, and chains for RAG-style pipelines; the trade-off above applies directly.
LlamaIndexSimilar idea, more opinionated about indexing/retrieval strategies; common for document-heavy RAG.
HaystackSimilar idea, leans more toward production search/QA pipelines.
Raw API calls (no framework)Full control, nothing hidden — but you write PDF parsing, chunking, and prompt assembly yourself.

Why this document loader, and what else fits?

It's a thin wrapper that's fast, dependency-light, and good enough for text-based PDFs — exactly the kind most technical papers and reports are. It struggles with two things: PDFs that are actually scanned images (no real text layer, needs OCR first) and PDFs with complex tables, where text can extract in a jumbled reading order.

OptionTrade-off / when to use it

pdfplumberThe PDF has tables you need extracted as structured data, not just flat text.

Quiz

Check yourself

1. What is a "chunk," and why is it usually smaller than a full page?

Smaller, focused chunks retrieve more precisely — a whole page mixing several topics pulls in noise along with the relevant part.

2. Why split text into overlapping chunks instead of clean, non-overlapping ones?

Repeating the tail of one chunk at the start of the next means a boundary sentence almost always survives intact in at least one of the two.

3. What's the risk of setting the overlap too close to (or larger than) the chunk size itself?

Overlap has to be meaningfully smaller than the chunk size, or you end up with near-duplicate chunks instead of genuine coverage of the document.
